# ADR-017 — Bound the debug loop three ways

**Status:** Accepted · **Phase:** 7 · **Date:** 2026-09-18

## Context

When a patch fails its tests, the agent can try again with the failure as
evidence. That loop is what makes this an agent rather than a pipeline.

It is also the single most expensive bug available in this project. Nothing in a
language model produces "I give up" — asked to try again, it always will — and
the budget is a free tier.

## Options considered

1. **No bound.** Loop until the tests pass.
2. **An attempt count.** Stop after N.
3. **A cost ceiling.** Stop after N tokens or calls.
4. **Progress detection.** Stop when attempts stop changing the outcome.
5. **Let the model decide** when to give up.

## Decision

**All of 2, 3 and 4**, independently enforced.

## Reasoning

Option 5 is the one to reject explicitly: a model asked "should you keep trying?"
will keep trying, and its answer is generated by the same process that produced
the failing patch. Termination cannot depend on the thing being terminated.

The other three are not redundant, because they fail in different ways:

**Attempt count** is the blunt bound. Always reached eventually, and it is the
one you can reason about when reading the code. It is also the *least* useful,
because it spends the whole budget before stopping.

**Progress detection** is the bound that actually saves quota. If an attempt
fails with the same signature as the last, the model is not making progress and
the remaining attempts will learn the same thing again. Measured behaviour: with
a limit of 5, an unchanging failure stops after 2 — three calls not spent.

**The cost ceiling** is what saves you when the other two have a bug. It sits in
the LLM layer, counts every call that reaches a provider, and does not care what
any loop believes. Defence in depth applied to spend rather than security.

### The failure signature

Progress detection needs "same failure" to be decidable. The signature is built
from **failing test identifiers**, not messages:

```python
return "tests:" + ",".join(sorted({f.test_id for f in validation.failures}))
```

Messages carry addresses, temp paths and timestamps that differ between
identical runs. Fingerprinting them would make two identical failures look
different and defeat the check entirely — the bound would be present and inert.

Sorted, so ordering does not matter either.

## Tradeoffs

**Against:**

- **Progress detection can stop too early.** Two attempts that fail identically
  might still be one step from a fix. Accepted: on a free tier, three saved calls
  are worth more than an unlikely third-attempt success.
- **The signature is coarse.** Different root causes producing the same failing
  test look identical. Making it finer would reintroduce the noise problem.
- **Three bounds is more code** than one.

**For:** termination is provable by reading `route_after_validation`, which is a
pure function over state; the expensive bound fires first; and a bug in the loop
cannot spend a day's quota.

## Consequences

- `route_after_validation` is a pure function, testable with a dictionary. "When
  does the agent stop trying?" does not require running a graph to answer.
- Failure signatures accumulate in state, so "this failed the same way twice" is
  answerable — and they are shown to the model as "approaches already tried".
- Eleven graph-level tests drive the real cycle and assert it terminates three
  different ways.

## Interview questions

**Q: What stops your agent looping forever?**

Three independent bounds. An attempt limit, which is blunt and always reached.
Progress detection — if an attempt fails with the same signature as the last, it
is not learning anything and further attempts will not either. And a call budget
in the LLM layer that bounds spend regardless of what any loop believes. The
second is the one that saves money: with a limit of five, an unchanging failure
stops after two.

**Q: Why not let the model decide when to give up?**

Because a model asked "should you keep trying?" keeps trying, and its answer
comes from the same process that produced the failing patch. Termination cannot
depend on the thing being terminated. That is also why the routing decision is a
pure function I can test with a dictionary rather than a judgement inside a node.

**Q: How do you decide two failures are "the same"?**

By the set of failing test identifiers, sorted — not the messages. Messages carry
addresses, temp paths and timestamps that differ between identical runs, so
fingerprinting them would make every failure look novel and the bound would be
present but inert. Coarse on purpose: the cost of stopping one attempt early is
much lower than the cost of a bound that never fires.

**Q: What does the loop actually feed back?**

The real test output, not a summary of it. If the model summarised the failure
and I fed the summary to the next attempt, the loop would be reasoning about its
own description of reality. I also list the approaches already tried, because
without that a third attempt is indistinguishable from a second.

## Behavioural question this answers

> *"Tell me about a time you designed for failure rather than success."*

The debug loop is the part of this agent that could spend a day's free-tier quota
in ten minutes if its bound had a bug, so I bounded it three separate ways rather
than once. An attempt count, which is the obvious one and the least useful.
Progress detection, which is what actually saves calls — if two attempts fail
identically the model is not learning and the rest of the budget will teach it
the same thing. And a call ceiling one layer down that does not trust the loop at
all. I also wrote eleven tests that drive the real cycle and assert it
terminates, because a loop you cannot prove terminates is the most expensive kind
of bug available in a project billed per call.
